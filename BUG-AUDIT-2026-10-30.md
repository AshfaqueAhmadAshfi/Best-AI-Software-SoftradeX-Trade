## 1. CRITICAL

### C1 — Trading-control API has **zero authentication**, and the documented deploy exposes it to the internet
`backend/app.py` (auth grep result: only `/api/ea/event` + `/api/ea/ping` call `_check_secret`, lines 888/896/921).

Unauthenticated and publicly callable:
`/api/connect` · `/api/disconnect` · `/api/settings` · **`/api/botN/start|stop|config|close`** for N=1..7 · `/api/ea-token`.

The only gate is client-side JS:
```
web/app.js:5813    if (input && input.value === '0186') {
```
That is a `<script>`-visible string, not security.

The exposure is not theoretical — `docker-compose.yml:29-31` publishes Caddy on `80`/`443`, `Caddyfile:22-24` has `basic_auth` **commented out**, and `app.py:1170-1173` switches to `0.0.0.0` as soon as `PORT` is set. `README.md:12-19` tells the user to run `docker compose up -d --build` and go live on a domain. Result: `https://<domain>/api/bot3/start` places **real orders on the live Exness account** from anyone on the internet. `app.py:1178` also advertises the public `/api/docs`.

**Fix:** add a server-side session/token dependency to every mutating `/api/*` route (reject when the session is locked), require auth on `/api/ea-token`, and uncomment `basic_auth` in the Caddyfile in the deploy docs.

### C2 — `/api/ea-token` hands out the bridge secret to any caller
```
backend/app.py:315    return {"ea_secret": cfg.CONFIG.get("ea_secret", "")}
```
The docstring argues POST-only stops drive-by browser reads, but that does nothing against a non-browser or same-origin caller. With the token, `POST /api/ea/event {"type":"close","trade":{...}}` writes arbitrary fake closed trades into the live account's history and P&L (`engine.py:1443-1446` → `store.upsert_trades`). No rate limit.

### C3 — Logging out does **not** stop Bot 6 and Bot 7
`backend/engine.py:424-490` stops and de-persists `running` for `bot`, `bot2`, `bot3`, `bot4`, `bot5` — verified there is no `bot6`/`bot7` block; line 480 is followed straight by `self._seen_open.clear()`.

Because the tick loop re-reads the persisted config every pass and fires on it:
```
engine.py:1605   if self.bot6.cfg.get("running") or self.bot6.enabled: ...
engine.py:1617   if self.bot7.cfg.get("running") or self.bot7.enabled: ...
```
…the comment at `engine.py:444` ("safety: logging out always stops the auto-trader") is false for magic 777006/777007. **A user logs out with Bot 6/7 armed, logs back in, and live trading silently resumes.** No test covers this.

### C4 — A transient MT5 read failure makes the straddle arm a *second* time
`backend/bot.py:446-449` and `466-472` swallow every exception as "no exposure":
```python
try: raw = mt5.positions_get()
except Exception: return []          # and identically for orders_get()
```
The tick then reaches the flat-state branch and re-arms:
```
bot.py:559   if positions or orders: ... return
bot.py:570   self._arm()
```
`_arm()` never re-verifies exposure. If the failing tick lands on a new M1 candle (the `_last_bar` guard at `bot.py:565-568` is the only brake), a second BuyStop+SellStop pair is placed. Four stops resting → both legs can fill → `bot.py:521` (`len(positions) > 1`) closes both at the spread loss. Same "exception ⇒ flat" shape in `trend_bot.py:813-816`, `entry_bot.py:552-555`, `reversal_bot.py:612-615`, `pretrade_bot.py:379-382`.

## 2. HIGH

### H1 — A bad numeric config value permanently silences a bot while the UI still shows `running: true`
`engine.py:1550/1566/1578` re-applies the persisted config on **every** tick. The coercion is unguarded:
```
trend_bot.py:258   self.cfg["lot"] = self._round_lot(float(self.cfg.get("lot") or 0.01))
trend_bot.py:259   self.cfg["max_trades"] = max(1, int(self.cfg.get("max_trades") or 1))
```
`"2.5"` or `"abc"` raises `ValueError`, which is caught one level up:
```
engine.py:1572   except Exception as exc:
engine.py:1573       self._log_event("error", f"Bot2 error: {exc}")
```
so `bot.tick()` at `engine.py:1570` is skipped forever and `status()` is never refreshed. `news_bot._f()` (`news_bot.py:208-215`) is the safe pattern the other modules should copy.

### H2 — `entry_bot` / `reversal_bot` ignore string-only config changes
```
entry_bot.py:142-146   def _same(a, b):
                           try: return abs(float(a) - float(b)) < 1e-9
                           except (TypeError, ValueError): return bool(a) == bool(b)
```
`"buy"` and `"sell"` are both truthy → `_same` returns `True` → `_relayout` is never set at `entry_bot.py:275-279`. So flipping **side buy→sell** leaves the already-parked pre-trade in the old direction and it still fires: a real order opposite to what the panel shows. `watch_gate` on→off has the same hole. `reversal_bot.py:164-168` + `300-304` repeats it for `timeframe` (M1→M5 never re-arms).

### H3 — Positions can be left with **no broker stop-loss at all**
```
entry_bot.py:173-174     "sl": 0.0            # pending pre-trade, no stop
reversal_bot.py:61       "sl": 0.0            # default config
pretrade_bot.py:599-600  "sl": 0.0, "tp": 0.0 # every ladder level
```
For bots 6/7 the broker SL is only attached once the trade is already ≥ $0.80 in profit (`entry_bot.py:937-966`), so a gap or open move has no floor. For the bot-4 ladder, only the deepest filled level is ever armed (`pretrade_bot._refresh_locks`), contradicting that module's docstring "a position is never left unprotected". Note `tests/test_entry_bot.py:174` currently *asserts* `sl == 0.0`, so a fix must update that test.

### H4 — `extreme_bot` dollar→price fallback mixes units
```
extreme_bot.py:207-209   if "XAU" in sym.upper() or "GOLD" in sym.upper(): return lot * 100.0
                         return 1.0
extreme_bot.py:720-721   tp_dist = round(tp_dollar / mpp, digits); sl_dist = round(sl_dollar / mpp, digits)
```
If `order_calc_profit` and `trade_tick_value` both fail on a non-gold symbol, mpp = 1.0 turns a **\$5.00 SL into a 5.00-price-unit stop** — either rejected (10016 invalid stops) or effectively absent. Every other module returns `0.0` and refuses to trade.

### H5 — News-bot stats double-count every self-closed trade
`NewsBot` has no `_self_closed` guard (grep: zero hits), so both sites fire for one close:
```
news_bot.py:1821   self.stats["closed"] += 1        # in _close_position
news_bot.py:2327   self.stats["closed"] += 1        # in _track, next tick
```
`closed`, `wins/losses` and `realized` are inflated ~2× for every scheduled exit. `entry_bot.py:807-808` shows the correct guard. `tests/test_news_bot.py:548` only asserts the `_track` half, which is why the suite is green.

### H6 — `RuntimeError: deque mutated during iteration` on `/api/chart/tape`
Writer on the 10 fps sampler thread, no lock:
```
chart_feed.py:1128   "prints": deque(maxlen=80)
chart_feed.py:1214   state["prints"].appendleft(print_row)
```
Reader on the **event loop** (its two siblings on the same line use `asyncio.to_thread`, this one does not):
```
app.py:969   "recent": chart_feed.recent_prints(symbol, limit)}
chart_feed.py:1264   return list(state["prints"])[:limit]
```
Once the deque is full, `appendleft` pops the tail mid-iteration → intermittent 500.

### H7 — Uncached failures + 8 s timeouts called in loops ⇒ feed dies when offline
`public_feed.py:39` `_HTTP_TIMEOUT = 8.0`, `:190` `urlopen(req, timeout=8)`. Only **success** is cached (`:380`); a failure walks the whole provider chain and raises (`:374`), so nothing negative is remembered and it retries immediately.
- `chart_feed.py:1137 → 865 → public_feed.tick()` runs on the same thread that does the WS fan-out (`_broadcast`, `chart_feed.py:1069`) → ~16 s blocked per pass.
- `market_watch.py:136-143` fetches up to **16 tickers serially** (`_PUBLIC_QUOTE_MAX = 16`) from `get_all_market_watches`, which `engine.py:1812` calls on every snapshot → worst case ~256 s for one tick, and the same function is the body of `/api/market-watch` (`app.py:411`), pinning the shared 40-worker `to_thread` pool.

This is the practical cause of "dashboard freezes on cPanel".

### H8 — Blocking MT5 IPC on the event loop, and `IPC_LOCK` held across network I/O
- `app.py:619` `bot3 = snap.get("bot3") or engine._bot3_stub()` — `_bot3_stub` runs `symbol_info_tick` + `compute_all_levels` synchronously on the loop and takes no `IPC_LOCK`, while `watch-stream` does take it (`market_watch.py:475`); the bridge is documented as not thread-safe (`mt5_client.py:29-32`). Same inline pattern at `app.py:522, 568, 672, 726, 790, 836`.
- `engine.py:245` holds `IPC_LOCK` across `_drain_commands`, and a bot-config command reaches `_compute()` (`engine.py:1812`) whose `get_all_market_watches` starts with a **public-HTTP prefetch** (`market_watch.py:819-820`). One Start/Stop click therefore stalls the 20 fps quote loop for the full provider timeout. `market_watch.py:821` likewise holds `IPC_LOCK` across the whole 10-symbol walk (each iteration does `terminal_info()` twice + `copy_rates_from_pos`).
- `app.py:233` `engine.submit("reload_history", {}, timeout=20)` runs before `yield` in the lifespan, so a cold start blocks the event loop for up to 20 s.

### H9 — Frozen-market detection never fires
```
market_watch.py:782   watches = [_calculate_symbol_watch_locked(s) for s in ...]   # max_ref_time never passed
market_watch.py:466   ref_time = max(float(max_ref_time or 0.0), now_utc.timestamp())
market_watch.py:468   if tick_time > 0 and (ref_time - tick_time) > 300.0:  # CLOSED
```
`max_ref_time` is `None` on the only production path, so `ref_time` is UTC while MT5 `tick.time` is broker server time (Exness UTC+2/+3). The difference is ≈ −10 800 s, never `> 300` → dials keep reporting **OPEN** through the daily break and through a halted feed.

### H10 — `/api/ea/event` GET duplicates trades
```
app.py:903-907    ... "ticket", "position_id", ... → payload[k] = float(v)
engine.py:1498    "position_id": str(pid)      →  "123456789.0"
```
`store.py:39` keys rows on `(account, position_id)`, so the GET path writes a second row for a trade MT5 already stored as `"123456789"` → duplicated `net_profit` in `/api/history`, stats and CSV export.
